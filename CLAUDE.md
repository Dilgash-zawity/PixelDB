# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Offline desktop database app in the spirit of MS Access: Tauri v2 + Rust (rusqlite, bundled SQLite) backend, SvelteKit 3 + Svelte 5 (runes) frontend, Tailwind v4 + shadcn-svelte UI, Bun as package manager.

## Commands

```sh
bun run tauri dev          # run the desktop app (also: bun run ddev)
bun run check              # svelte-check / TypeScript — keep at 0 errors, 0 warnings
bun run test               # all tests: bun test src && cargo test
bun test src/lib/logic/table-draft.test.ts            # one TS test file
bun test src -t "renames propagate"                   # TS tests by name
cargo test --manifest-path src-tauri/Cargo.toml --test phase1 add_modify   # one Rust integration test
cargo test --manifest-path src-tauri/Cargo.toml --lib validation::values   # Rust unit tests by path
cd src-tauri && cargo clippy --all-targets            # keep warning-free
bunx tauri build --debug --no-bundle                  # build the app binary without installers
bunx --bun shadcn-svelte@latest add <component>       # add a UI component
```

The shadcn-svelte CLI prompts interactively and has no TTY in agent shells; drive it with `expect` (or a small Python `pty` script where `expect` isn't installed), answering `y` to "Ready to install components and dependencies?" (Enter alone cancels it) and Enter on idle for other prompts.

## Architecture

**IPC boundary.** All database work is in Rust. `src-tauri/src/commands/*` are thin `#[tauri::command]` wrappers that run `database::*` functions on a blocking thread via `DbManager::run`. The `database/` functions take a plain `&rusqlite::Connection` and know nothing about Tauri, which is why `src-tauri/tests/phase1.rs` can test them against real temp-file databases. Errors are `errors::AppError`, serialized as `{ kind, message }`; the frontend turns them into `ApiError` (`src/lib/api/client.ts`) and toasts (`state/feedback.svelte.ts`, with `logic/messages.ts` rewriting raw SQLite constraint text into plain language).

**Wire types are hand-mirrored.** `src/lib/api/types.ts` mirrors `src-tauri/src/models/*`. Serde shapes (tagged enums like `FieldType`, `DefaultValue`, `RecordKey`) are pinned by `wire_format_tests` in `models/mod.rs`; update both sides together. Tauri converts command argument names to camelCase on the JS side (`newName`, `confirmDataLoss`), while nested struct fields stay snake_case.

**Workspace model.** The user picks a folder once (remembered in the app config dir by `workspace::WorkspaceStore`). Databases are created/opened **by name** inside that folder — the frontend never passes database file paths, and names are resolved from a directory listing, not by joining user input. `DbManager` is a registry of open connections keyed by canonical path (one mutex per database) plus the *current* database of the database page. Commands act on the current one by default; record, `list_objects`, `get_table`, `run_query` and `get_query` commands also take an optional `database` name (frontend: the last argument of the service call, sent via `on()` in `api/client.ts`), opening that file into the registry on demand — that is how apps use several databases at once. `release_databases` closes everything but the current one (called when leaving an app and on the home screen); renaming/deleting a database closes it wherever it is open.

**Online databases** (`src-tauri/src/connections.rs`, `src-tauri/src/remote/`, `logic/connections.ts`). Besides local files, a user can save connections to PostgreSQL, MySQL, SQL Server, a libSQL/sqld server (shown as "SQLite server"), Supabase, Neon and Turso (`Provider`; each maps to one `Engine`: Postgres via sqlx, MySQL via sqlx, SQL Server via tiberius, libSQL via the Hrana HTTP pipeline with reqwest). Connections live in the app config dir's `connections.json` (written 0600, never in the workspace folder, the same in every folder); the frontend gets `ConnectionInfo` without password/token, and an empty secret on save/test with `previous` keeps the saved one. Names are unique across local and online databases (`workspace.nameTaken`, `save_connection`). Online databases are **read-only** for now: `remote_tables`, `remote_preview` and `remote_query` (one statement, checked by `remote::sql::read_only_statement`, then run inside `BEGIN READ ONLY`/`START TRANSACTION READ ONLY`, or BEGIN…ROLLBACK on SQL Server and libSQL; 1000-row cap, 15 s connect + 30 s timeout); every call opens and closes its own connection. sqlx futures aren't provably `Send` inside a command, so `commands/connections.rs` drives them with `block_on` on a blocking thread (`online`). They aren't app sources yet. UI: `NewDatabaseDrawer` (Where → Database → Connection → Name; local is Where → Name; editing is Connection → Name; a pasted connection string fills the form via `parseConnectionString`; finishing tests the connection first, with "Save anyway" after a failure), `ProviderIcon` (brand logos, colored only outside Focus mode), cards on the home map without connect handles, and `routes/online/+page.svelte?name=…` (table list by schema, Data preview of 200 rows, SQL tab). `live_postgres` in `commands/connections.rs` is an ignored test against a real server (`SLATEDB_TEST_PG=host:port:user:password:database`).

**Apps** (`src-tauri/src/apps.rs`, `logic/app-def.ts`). An app is a JSON file `<workspace>/Apps/<name>.baseapp`, addressed by name like databases (list/create/load/save/rename/delete-with-`confirm`/duplicate commands; saves are write-then-rename). The backend stores the definition opaquely, checking only `version` (newer formats are refused) and size; `readApp` on the frontend fills defaults and drops unknown widget types. An app has `sources` (alias → database name; widgets name the alias, so a database rename only touches sources — `rename_workspace_database` rewrites them in every app), app-wide `variables`, sidebar `commands` (label + icon + action), and pages of widgets on a 12-column grid (`logic/app-layout.ts`: place/compact/findSpot). Pages carry an `icon` (one of `ICONS`, rendered by `AppIcon.svelte`), a sidebar `group` heading and `hidden`; "New page" starts from a `PAGE_KINDS` kind (`addPageOfKind`: list, form, list-and-form, query, dashboard, blank). Widgets: table (optional `badges` columns shown as colored `ValueBadge` labels, toned by a hash of the value; headings sort on click in Run mode), form, board (kanban: cards in a lane per value of `groupBy`, lanes from `logic/board.ts` — a relation's records, No/Yes, the configured `lanes`, then other values found and "None"; dragging a card with pointer events updates that field; tables only), chart, stat (number card), filter (a control that sets a variable), button, text (a small Markdown subset parsed by `logic/markdown.ts` and rendered as elements, never HTML), query (read-only SQL run through `run_query` with a `params` map: `:name` in the SQL is bound from the app variable `name`; `sqlParameters`/`mapSqlParameters` find and rename them outside quotes and comments). Definitions are declarative only: data comes from `list_records` and `aggregate_records` (structured grouped totals built in Rust from column names, `records::aggregate`; currency sums/averages stay integer minor units) with filters whose values are literals or variables (`resolveFilters` drops filters on empty variables so an unset control shows everything); actions are navigate/set-variable/edit-record/new-record/refresh/print. Renaming a table or field on the database page calls `state/app-sync.ts` to update every app using that database; `widgetProblems` explains bindings that no longer resolve, and widgets show that instead of erroring. `logic/templates.ts` defines starter databases + apps (created by `workspace.createFromTemplate`). `logic/app-generate.ts` `generatePages` builds pages from table definitions (`tableService.listDefinitions`): per table a list that sets a `selected_*` variable, a form filtered by it (quick entry: blank until a row is picked; `FormWidget.quickEntry`, Enter adds and clears, saving an edit clears the key-filter variable) and tables of linking child records underneath, a board for status-like fields, junction tables skipped, and an overview on an empty start page; used by "Build a page for each table" in `NewAppDrawer` (a StepDrawer: Start → Name → Data → Review; templates skip Data), the Data tab's wand button and the empty start page (`appSession.buildPages`). Generated pages carry an `origin` (source, table, kind, the fields and linking tables seen, the pick variable; null on hand-made and duplicated pages). A source with `auto` ("Update automatically" in the Data tab, switched on by building pages) is kept in step by `syncGeneratedPages`: pages for new tables, removed pages/variables for deleted ones, new fields appended to list columns (not ones the user took out), deleted fields pruned from every widget on that source (boards on a deleted lane field go), new linking tables added under their parent; saved queries are left alone and the overview isn't refilled. It runs after every structure change on the database page (`tableService.onStructureChange`, emitted by create/drop/saveDesign/add/modify/drop field — renames instead go through `renameTableInApp`/`renameFieldInApp`, which also update origins; `session` debounces into `syncAutoApps`, and `updateApps` serializes all app-file rewrites) and when an app opens (`appSession.syncAuto`, not an undo step). In Edit mode a selected widget moves with the arrow keys (Shift resizes; `appSession.nudgeWidget`), ⌘D duplicates, ⌘C/⌘X/⌘V use `appSession.clipboard`, a `CopiedWidget` (the widget plus its app's sources and variables) that `adaptPastedWidget` fits into the target app (same database, adding it if needed; missing variables created; links to pages/widgets it lacks become "none") — these, Delete and Escape apply only while focus is on the canvas or page sidebar (`data-canvas`, `data-app-sidebar`), not in menus or the panel. `appSession.guard(id, check, reads)` also runs before a set-variable/navigate action changes a variable a dirty form reads, so unsaved typing is never dropped silently; quick-entry forms without a linked list browse records with ◀ ▶.

**Access-style types on SQLite.** SQLite has no Currency/Yes-No/etc., so each table's `TableDef` (field types, descriptions, relations) is stored as JSON in the hidden `__app_tables` table alongside the exact `CREATE TABLE` text it produced. `schema::load_table` trusts that metadata only while the stored SQL matches `sqlite_schema`; otherwise it infers a definition from pragmas and reports `unsupported_features` (CHECKs, collations, WITHOUT ROWID…), and structural redesigns of such tables are refused so constraints are never silently dropped. Names starting `sqlite_` or `__app_` are reserved and hidden.

**Schema changes** (`database/migrations.rs`). Column renames use `ALTER TABLE RENAME COLUMN` and propagate into stored metadata (including other tables' FKs and lookup display columns). Anything else goes through `save_table_design`, which follows SQLite's 12-step rebuild: foreign keys off (`ForeignKeysOff` guard, set *outside* the transaction), create temp table, copy with type conversions (`convert_expr`, e.g. currency minor-unit scaling), drop, rename under `legacy_alter_table`, recreate indexes/triggers, restore the AUTOINCREMENT sequence, then fail the whole transaction if new `foreign_key_check` violations appear or a previously working view breaks.

**Safety rules baked into the API.** User values are always bound parameters; identifiers go through `validate_identifier` + `quote_ident`; SQL fragments accepted in DDL (CHECK, DEFAULT, formulas) pass `validation::expressions::validate_expression` (no `;`, comments, subqueries, or unbalanced parens). Destructive operations (drop table/field, delete records, design saves that remove fields) require an explicit `confirm` flag in the backend, not just a UI prompt; new database files use `create_new` so nothing is overwritten. Currency crosses the API as integer minor units or decimal strings parsed exactly.

**Frontend layers** (`src/lib/`):
- `services/` — typed wrappers around `invoke`.
- `logic/` — framework-free, unit-tested business logic: `table-draft.ts` (design edits → `TableDesign` with rename tracking, used by `relationships.ts` for single-field edits), `record-buffer.ts` (per-record edit buffer with field/record undo and submission rules), `filters.ts`, `lookups.ts`, `values.ts`. Put new non-UI logic here with a `*.test.ts`. Use `jsonClone`, not `structuredClone` — the latter throws on Svelte `$state` proxies.
- `state/` — rune-based singletons: `workspace` (also the app list and app create/rename/duplicate/delete), `session` (open DB, current table, `tab: 'diagram' | 'datasheet' | 'query'`, the Query tab's `query` draft), `appSession` (`app.svelte.ts`: the open app, Edit/Run `mode`, current page, selected widget, run-time `vars`, `dataRevision` to make data widgets reload, cached schemas per source, `change(edit, group)` with undo/redo via `logic/history.ts` and 500 ms autosave, `guard()` for forms with unsaved edits), `feedback` (toasts + a promise-based `confirm()`).
- Theme tokens live in `src/app.css`. The default is a **colorful** theme (a calm blue primary, barely tinted surfaces, 8px corners, muted `--tone-violet/blue/cyan/green/amber/pink` category colors used for icons and badges; deliberately no gradients, glows, gradient text or colored shadows — color comes from solid tokens only). The first-run screens (welcome and empty home map) show `FocusModeSwitch.svelte` so people can pick a look up front. **Focus mode** (setting `focusMode` → `data-focus` on `<html>`) drops all of that back to the original neutral grey theme with square corners: the colorful token blocks are `:root:where(:not([data-focus]))`/`.dark:where(…)`, and component-level color uses the `vivid:` Tailwind variant on top of the plain classes (e.g. `bg-muted text-muted-foreground vivid:bg-tone-cyan/15 vivid:text-tone-cyan`), so Focus mode must look like the classes without `vivid:`. The Corners setting's default `auto` means rounded when colorful, square in Focus mode. Both looks share status colors `--destructive` (red: delete/remove, errors), `--warning` (amber: read-only and check-before notices, primary-key icons) and `--success` (green). Use `variant="destructive"` for danger actions and `text-warning`/`border-warning/40 bg-warning/10` for warnings. The logo is `src/lib/assets/logo.svg`; app icons in `src-tauri/icons` are generated from a 1024px render of it with `bunx tauri icon`.
- `components/ui/` — generated shadcn-svelte components; change via the CLI rather than hand edits. `components/app/` — app screens composed only from those.

**Screens.** `routes/+page.svelte` is the home screen: a top bar (logo, settings, theme — the workspace folder path is shown only in Settings) over a full-screen canvas (`components/app/WorkspaceMap.svelte`) of app and database cards, card positions in localStorage per folder (`logic/workspace-map.ts`), a line for each app's source drawn with the diagram's `edgeRoute`; drag a card's dot onto the other kind to connect (`workspace.connectApp`/`disconnectApp` edit the app's sources), right-click to create here, tidy up or fit (the app is named **Base**); `routes/app/+page.svelte?name=…` is an app: top bar (sidebar toggle ⌘B, app switcher — other apps and Home, no Settings; Settings is in ⌘K, current page, save status, undo/redo, Edit/Run toggle, ⌘K `AppCommandPalette`), the left `AppSidebar.svelte` (pages by group and the app's actions; collapsible to icons, remembered in localStorage `slatedb.appSidebar`; in Edit mode pages drag to reorder/regroup with pointer events, not HTML5 drag-and-drop, and clicking an action selects it), `AppCanvas.svelte` (grid, drag to move, corner to resize, Delete/⌘Z/⇧⌘Z) and, in Edit mode, a fixed right panel: `WidgetProperties.svelte` for a selected widget, `CommandProperties.svelte` for a selected action, else `BuilderSidebar.svelte` (Add / Page: name, icon, heading, visibility, start page / Data: databases and variables / Style: accent and description; tab in `appSession.builderTab`). Properties panels are not drawers, built from `PropSelect`, `BindingPicker`, `IconPicker`, `ColumnPicker`, `FiltersEditor`, `ValueRefInput`, `ActionEditor`); each widget renders through `WidgetFrame` → `*WidgetView.svelte`. Data widgets key their fetch effect on the JSON of the request so unrelated variable changes don't reload them; table rows edit through `RecordDrawer` (which takes `database`, `prefill` and `allowDelete`). Accent colors are `--app-accent` set by `data-accent` in `app.css`. The database page is `routes/db/+page.svelte?name=…` (query params keep routes prerenderable). `routes/settings/+page.svelte` (linked from the home header, the database and app switcher menus and the app command palette; Back uses `history.back()`) has Workspace (root folder + change, reset the home map layout), Appearance (theme via mode-watcher, accent, corners, text size), Behaviour (reduce motion, canvas hints) and About (version from `getVersion()`, i.e. `tauri.conf.json`'s version, and the author link opened with `@tauri-apps/plugin-opener`, whose capability allows only https://dilgash.com). Look-and-feel preferences live in `state/settings.svelte.ts` (validated by `logic/settings.ts`), stored in localStorage `slatedb.settings` and mirrored as `data-ui-accent`/`data-radius`/`data-text`/`data-reduce-motion` on `<html>`, which `app.css` keys on; an inline script in `app.html` applies them before first paint, so keep it in sync with `settingsAttributes`. The database page has no sidebar and no Design view: it has a top bar (database switcher with "New database…", search, theme) and three tabs, `session.tab`: **Diagram** (`RelationshipsView.svelte`), **Datasheet** (`RecordsView.svelte`, with a table picker in the top bar) and **Query** (`QueryView.svelte`). The page shows a skeleton until `session.name` matches the route and `session.info` is loaded, because views fetch data as soon as they mount. The Query tab has a visual designer (`logic/query-builder.ts`: tables joined along relationships, columns with sort/totals/criteria turned into SQL with typed literals) and a SQL editor. `database/queries.rs` runs only a single read-only SELECT/WITH/VALUES (checked with `stmt.readonly()`), caps results at 1000 rows and interrupts after 30 s; saved queries are plain views (`save_query` needs `replace` to overwrite one, `drop_query` needs `confirm`); a query saved from the designer also stores its `VisualQuery` JSON in hidden `__app_queries`, and `get_query` returns it only while the view's SQL still matches what was saved (else it opens as SQL). The Query tab lists saved queries in a left sidebar. Query results and view pages carry `types` (each column's field type traced to its source table via rusqlite's `column_metadata`, `schema::result_types`), so money and Yes/No display correctly outside the designer; text filters and search compare currency/Yes-No as displayed (`12.50`, `Yes`), in both `records.rs` and the designer. In `records.rs` they also ignore case in every alphabet through `slatedb_fold`, a Unicode lower-case function registered on each connection in `open_connection` (only in queries the app builds — never put it in saved views or other schema SQL, or the file breaks in other SQLite tools); sorting a relation field orders by the linked record's display column (`display_sort`), then the stored ID. All structure editing happens on the Diagram: add/rename/delete tables (dialogs), click a field or "Add field" to open `FieldDrawer.svelte` (Name → Type → Rules, type cards from `FieldTypeCards.svelte`, rules via `FieldProperties.svelte`; saves through `fieldDesign`/`withoutField`), click a table or line to open the details drawer (`RelationshipPanel.svelte`: a table as Table → Fields → Links, a relationship as Kind → Rules), right-click the canvas, a table, a field or a line for a context menu, drag a field's dot onto another table to propose a link (`logic/relationships.ts` `proposeLink`), which opens `NewLinkDrawer` (Tables → Kind → Details). Every link change is a `save_table_design` of the child table (FK + optional lookup field, or a junction table for many-to-many). Card positions are saved in `__app_meta` (`metadata::save_layout`). The Datasheet's column menu also opens `FieldDrawer`. Every drawer is `StepDrawer.svelte`: full screen from the bottom with a `Stepper`, Back/Next and a finish button — no right-hand drawers and no Sheets; dialogs only for short prompts. `NewTableDrawer`: Name → Fields (a card per field; clicking one, or "Add field", opens `DraftFieldDrawer` nested on top — `StepDrawer nested` — with Name → Type → Rules on a copy of the field; Quick add chips add ready-made fields directly) → Review, creating ID + fields in one `create_table`; `NewFieldDrawer`: Name → Type → Rules, or → Link when the type is Relationship (adds the lookup field and FK with `linkDesign`), shown by `FieldDrawer` when `field` is null; checks in `logic/table-wizard.ts`; `RecordDrawer`: the fields five per step (`fieldPages`) then Review; delete/remove/unlink buttons and menu items use `variant="destructive"` (red); a confirm opened inside a drawer must pass that drawer's `scope`, which `StepDrawer` renders as `<ConfirmHost scope=…>`. The Datasheet registers `session.leaveGuard` so switching tables/tabs/databases first commits the row; navigation is serialized so a guard can't run twice. The command palette talks to the open datasheet through `session.request(...)` / `session.intent`.

## Conventions and gotchas

- SvelteKit 3 removed `$lib`; use the `#lib/...` package import (shadcn components import `#lib/utils.js`). Within `src/lib`, relative imports are also used so `bun test` resolves them.
- `adapter-static` with `fallback: 'index.html'`, `ssr = false`, `prerender = true` in `+layout.ts`.
- Follow the project shadcn-svelte skill (`.claude/skills/shadcn-svelte`): `class` only for layout, semantic color tokens, `gap-*` not `space-*`, `data-icon` on icons inside buttons, items inside their `*.Group`, no manual z-index on overlays. A confirm opened from inside a Sheet or Drawer must use a scoped `<ConfirmHost scope=…>` rendered inside its content, or it stacks behind it.
- An `$effect` that calls an async loader (e.g. `appSession.open(name)`) must `untrack` the call: state the loader reads before its first `await` otherwise becomes a dependency, and every edit re-runs the loader.
- Don't `bind:checked` to a possibly-undefined property (Svelte throws `props_invalid_value`); use `checked={!!x}` + `onCheckedChange`.
- Dark mode is the first-run default via a tiny script in `src/app.html` that seeds mode-watcher's localStorage key; `defaultMode` alone doesn't work in this client-only app.
- Tauri capabilities expose only `core:default`, `dialog:allow-open` (folder picker) and `opener:allow-open-url` scoped to https://dilgash.com; there is no filesystem plugin. Production CSP is set in `tauri.conf.json` (`devCsp` is null for Vite HMR).
